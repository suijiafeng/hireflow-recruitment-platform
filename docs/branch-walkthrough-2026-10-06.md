# 分支流程与未覆盖角色走查（2026-10-06）

上一轮全流程只走了「一个候选人一路顺利入职」。本轮补上没走到的门户、Offer 分支、自定义角色、一人多角色和账号停用。

走查方式：
- 主要通过 HTTP 接口按角色逐步操作，在每个交接点核对状态与通知。
- 前端代码对照确认页面会怎么显示。
- 自定义角色、多角色、停用账号三项在**临时起的真 Postgres** 上跑（本地 `postgres:18-alpine` 容器 + 第二个 API 实例，跑完已删除），避免 PGlite 的干扰（见文末）。

## 结论一览

| 场景 | 结果 |
|---|---|
| A 简历预筛门户 | 门户与规则校验正常；**后台看不到预筛结果**；通知只链到 `/pipeline` |
| B 面试自助选时（两位面试官） | 取交集、占位、重复选时拦截都正常 |
| C 取消面试 | 时段正确释放、面评被拦；**候选人门户仍显示「面试时间已确认」** |
| D 两位面试官各交面评 | 通知、结论并存正常；修订面评仍叫「已提交」 |
| E Offer 驳回 → 重提 → 拒绝 | 全部正常，指定用人经理时只通知他 |
| F 拒绝 Offer 后重新激活 | 激活正常；**激活后无法再发 Offer** |
| G Offer 过期 → 续期 → 接受 | 全部正常 |
| H 自定义角色（本部门招聘专员） | 数据范围、薪资脱敏都正确；**收不到任何招聘通知** |
| I 一人多角色 | 取最宽范围正确；**改角色 / 降权后旧令牌最长 12 小时仍按旧权限** |
| J 停用账号 | **没有停用入口**；停用后审批通知仍只发给已停用的人 |

## 待处理问题

### P1 会让流程走错或卡住

1. **取消面试后，候选人门户仍显示「面试时间已确认 10-07 14:00」。**
   - 取消只把状态改为 CANCELED，`scheduledAt` 保留。门户只要看到 `scheduledAt` 就渲染成已确认。
   - 候选人没有其他渠道得知取消，会按原时间到场。
   - 建议：门户按 `status` 显示「面试已取消，请等待 HR 联系」；取消时清空或单独标记时间。

2. **重新激活的候选人无法再发 Offer。**
   - Offer 与应聘记录是一对一（`applicationId` 唯一）。候选人拒绝后，旧 Offer 仍挂在这条记录上，再发起报「该应聘记录已存在 Offer」。
   - 激活这个动作本身没有意义了：人回到了流程里，却走不到录用。
   - 建议：Offer 已终结（拒绝 / 过期未续）时，允许新建一份并把旧的归档；或改为一对多，只保留一份在途。

3. **后台看不到预筛结果。**
   - 候选人提交的期望薪资、到岗时间、是否接受出差、不符项，只存进了应聘记录，后台没有任何页面展示。时间轴上只有「候选人提交预筛」一行。
   - 通知写着「请人工判断是否继续邀约」，HR 却无处可判断。
   - 建议：候选人详情的应聘卡片里展示预筛结果，看板卡片标出不符项；通知链接直达该候选人。

4. **账号无法停用。**
   - 数据库有 `ACTIVE / DISABLED`，设置页也显示「启用 / 停用」，但没有任何按钮或接口能改。员工离职只能直接改库。
   - 直接改库后的表现：
     - 旧令牌立即失效，这一点正确。
     - 职位上挂的用人经理不会被替换。本例 4 个职位仍挂着已停用的林涛。
     - **Offer 审批通知只发给了已停用的林涛**，没有任何在职的人收到。「职位负责人」兜底规则没有检查在职状态。
     - 新建职位时，「用人经理」下拉里仍能选到已停用的人。

5. **改角色、降权后，最长 12 小时内仍按旧权限放行。**
   - 权限码写在登录令牌里。JWT 守卫每次只查账号状态，不查角色。
   - 实测：把苏晴从「面试官 + 用人经理」降回「面试官」后，她的旧令牌仍能看到 11 份 Offer。
   - 升权同样要重新登录才生效。
   - 建议：守卫按用户重新加载角色与权限（可加短时缓存），或改角色时让该用户的令牌失效。

6. **自定义招聘角色收不到任何通知。**
   - 「面评已提交」「Offer 已接受」「材料已交齐」等都是按角色码 `HR` 推送的。管理员新建的「部门招聘专员」能看、能操作，却收不到任何提醒。
   - 建议：按权限推送（例如有 `offer:initiate` 的人负责 Offer 相关通知），并结合数据范围过滤，只通知本部门的人。

### P2 让人困惑

7. **通知里的时间写死服务器时区，并带秒。**
   - 例：「2026/10/7 14:00:00」。本机是北京时间所以看起来正常；容器默认 UTC，会差 8 小时。
   - 涉及「新面试指派」「候选人已确认面试时间」。
8. **修订面评仍推送「面评已提交」。** HR 分不清是新面评还是改过的。
9. **「面试已取消」通知正文为空。** 没说是谁取消的、原定什么时间。
10. **候选人被淘汰后，预筛链接仍能打开表单。** 填完提交才提示「已不在流程中」。

## 验证通过的点

- 预筛：
  - 链接复用同一令牌。
  - 非法输入被拦截。
  - 不符项判定正确（到岗超 60 天、不接受出差）。
  - 重复提交被拒。
- 自助选时：
  - 两位面试官取共同空闲。
  - 选定后两人的时段都被占用。
  - 不能二次选时。
  - 两位面试官与 HR 都收到通知。
- 取消面试：时段全部释放；已取消的场次不能再交面评。
- 多面试官：两份结论（推荐 / 不推荐）并存显示；HR 与用人经理各收到两条通知。
- Offer：
  - 驳回必须填意见；HR 不能自己审批；被驳回的不能发送。
  - 重提必须带入职日期。
  - 拒绝必须选原因，拒绝后不能再接受。
  - 拒绝后应聘置为「已撤回」，并提示补充招聘。
  - 过期后门户显示失效、接受被拒、HR 收到失效通知；续期只能一次；续期后可以接受。
- 自定义角色：
  - 本部门范围对职位、候选人、看板、Offer、入职单、大盘都生效。
  - 没有 `salary:view` 时薪资被隐藏。
  - 缺少的权限会明确提示「缺少权限: job:create」。
- 多角色：重新登录后取最宽范围，可见候选人从 11 人增加到 45 人，且只限本部门。
- 停用：旧令牌立即 401，不能再登录。

## 关于 PGlite 的误报

走查中一度看到「淘汰 / 撤回的候选人无法重新激活（409）」。排查结果：
- API 进程内，按联合唯一键查询拿到了别的查询的结果集。报错原文是「Missing data field 'candidateId'; data: {id, status}」。
- 同样的代码单独运行、或换成真 Postgres 跑，都正常。

原因是本地 PGlite 单会话在多条连接下串结果。走查脚本直接连库改数据会触发这个问题，并且影响会持续到 API 重启之后。这不是业务 bug，但说明：
- 本地开发库只适合单连接、只走 HTTP 接口；需要直接改库的测试应在真 Postgres 上做。
- 上线环境用的是真 Postgres，不受影响。
